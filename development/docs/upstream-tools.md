## y3-tools 的三个工具

### 物编 JSON 表格生成

读取 `config.json` 中的物编表、`excel/<table>.xlsx` 的 def 表及 JSON 模板，将结果写入地图 `editor_table`，同时更新中英语言哈希。Excel 要求 key/uid 为一致整数，并有描述字段。README 中关于“主关卡合并”的句子沿用了另一工具说明，实际职责以 `main.py` 的生成流程为准。

**本工程先用新版官方 y3-obj-edit**：现有小规模物编调整已经可以由 Python 3 脚本完成并已隔离测试，不增加 Python 2.7 运行环境及旧版 Excel 依赖。以后确有策划批量 Excel 工作流时，复用其格式规则，先在独立工程验证新字段、tuple 和语言哈希，再接入；不重新凭空编一套格式。

### 多场景物编转移

从主地图向其同级目录的其他地图复制所选物编、对象触发器、语言数据、物编目录和属性/伤害/规则数据；配置开启全局触发器时还会先移除目标 global_trigger 目录再复制。它是覆盖式合并，不是跨版本智能迁移。

**当前只有 EntryMap，无需启用**。源码中的 `merge_rule_data` 在读取目标规则前已复制整个源规则文件，实际影响超出后续列出的 rule_keys；未来使用必须先关闭工程、备份并在隔离副本检查差异，不能以工具名推断只改物编。

### 美术与程序拆分开发

把美术场景的地形、摆件、灯光/环境等文件同步到逻辑地图，并合并 `logicres.json`，保留代码指定的一组逻辑资源类别。README 要求先由资源管理器导出/导入模型资源，再执行场景同步；因此它不负责完整资源依赖迁移。

**当前没有独立美术分支地图，不启用**。存在成对美术/逻辑场景时可借鉴其文件集合与逻辑资源保留规则，先核对当前 Y3 版本的数据结构，不能把它当通用部署脚本。

## 运行时属性面板

README 将其定位为 Y3 2.0 编辑器扩展，通过资源商城或自定义编辑器插件装载。入口 `Script/EditorPlugin/main.py` 依赖编辑器注入的 `G` 与 PyQt5，注册暂停/恢复、编辑与游戏模式切换、单位选中等事件；显示单位、物品、可破坏物的属性和 KV，暂停时可修改。

它适合开发时观察属性，不是玩家使用的契灵管理面板，也不是 Codex MCP 服务。现阶段开发助手的日志/执行 Lua/截图已覆盖主要调试路线，先不安装第二套调试 UI，不将约 56 MB 插件源码与资源打入地图。将来需要人工观察实时属性时优先使用编辑器支持的插件安装方式；本次没有修改编辑器安装目录或启动插件。

## 开发助手与 Codex

缓存源码 `src/mcp/mcpInfo.ts` 明确提供 `http://127.0.0.1:8766/mcp` 的 Codex 配置。助手服务可提供游戏状态、日志、Lua 执行、截图、Lua 诊断和 UI 树；以实际 `tools/list` 为准。编辑器本身的 8765 接口与开发助手 8766 是不同服务，不能由其中一个响应推断另一个已连接。

这次实际观察到 VS Code 扩展 `sumneko.y3-helper@2.4.0`，而源码 package.json 为 2.4.1。故仅确认“扩展已安装”和“源码支持 Codex”；未通过端到端连接前不能声称安装版本提供了相同全部接口。没有在此次评估中改变全局 Codex 配置或启动游戏。
