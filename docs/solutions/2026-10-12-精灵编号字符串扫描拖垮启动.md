# 精灵编号字符串扫描与开局中断

## 现象与环境

用户报告第一波不出生、镜头不聚焦农民。第一轮把 HUD 创建和刷新从启动线程中隔离后，用户确认问题依旧，且最新地图没有 HUD。项目为 JASS/v1.28，运行环境为 Warcraft III 1.27a。

## 无效尝试与关键线索

第一轮依据“农民与面板出现”的描述，怀疑重复完整 HUD 刷新耗尽启动预算。隔离 HUD 是可验证的结构改善，但没有解决故障。后续“最新地图无 HUD”的信息将中断位置提前到 `tdSetupPets` 等启动步骤。

此前离线启动验证把 `tdSetupPets` 作为桩跳过，只能证明调度边界，不能证明整段启动能完成。这是验证盲区；通过该验证不代表游戏已恢复。

## 确定的高开销根因

`tdPetSetupUI` 在同一个启动线程注册 153 个技能事件，其中 151 个编号由 `TDPetData.tdPetHexRawcode` 动态拼接字符串，再调用标准库 `fromRawCode` 转成整数。标准库对四个字符分别在线性 `CHARMAP.indexOf` 中搜索。

执行修复前实际打包 JASS 的 151 个编号生成函数，得到 376,620 个离线解释器语句步骤、604 次 `string_indexOf`、46,223 次 `SubString`。仅首个编号就有 294 次 `SubString`。这些不是引擎 operation 数，但明确证明启动存在大批重复线性扫描。首波、HUD 和镜头继续均排在它之后，现象与 JASS 线程超预算一致；实际引擎中断位置仍需用户实测确认。

## 修正

- 编号前缀用已有 `xx00` 整数字面量，两个十六进制字符分别计算 ASCII 差值，再加到对应字节。保留所有原编号与边界行为，不更改物编命名空间。
- Wurst 测试逐个比较全部 151 个启动编号，以及显示单位和预览技能编号。
- `VerifyPetStartupArtifact.py` 执行真实打包的 `tdPetSetupUI`，检查完整 153 次注册、重复初始化幂等、无字符串扫描；触发器注册和计时仍为明确桩。与旧图比较 W3A/W3U 字节。
- 原 `VerifyStartupArtifact.py` 不再跳过精灵 UI 初始化，将其纳入启动到首波及镜头继续的检查。
- 增加独立 5 秒原生启动检测计时器。启动完成时取消；中断时显示最后正在执行的阶段，不吞掉错误或继续半初始化状态。

## 验证与残余风险

`tools\Run-WurstChecks.bat`：类型检查和全部 Wurst 测试通过。`VerifyPetManagerSource.verify_scalar_contracts()` 通过，覆盖完整能力分区及边界。旧图不能通过新增的“启动禁止字符串扫描”检查。

`build-and-deploy-test-map.bat` 编译与部署成功，显示名“深渊守望 2245”，目标为 `D:/War3_1.27a/Warcraft III Frozen Throne 1.27a publish/Maps/Test/深渊守望.w3x`。

`python -X utf8 tools/VerifyPetStartupArtifact.py ExampleMap.w3x --baseline <修复前地图>`：153 个事件注册完整且重复初始化无重复注册。包含实际 UI 初始化的离线解释器步骤从 377,869 降至 4,869；字符串搜索从 604 降至 0，字符串截取从 46,223 降至 0。两张地图的 W3A、W3U 字节完全一致。前述 376,620 仅统计编号生成，377,869 还包含 UI 初始化其他代码；两者范围不同。

`python -X utf8 tools/VerifyStartupArtifact.py ExampleMap.w3x`：真实精灵 UI 初始化、首波 epoch、镜头继续、HUD 合并刷新和启动检测计时器生命周期均通过。独立检测覆盖未完成时提示、旧计时器不影响新局及成功启动取消检测。

本轮按当前仓库规则为普通局部修复，由当前主代理直接实现验证，不新增协作阶段。未启动或控制游戏；尚不宣称用户场景已经恢复。若仍失败，独立启动检测将提供更精确阶段。

## 可复用经验与可提炼技能

启动回归不能把最昂贵的系统初始化整体替换成空桩。对看似简单的字符串工具追到标准库实现：批量 runtime rawcode 转换可能隐藏线性扫描；固定格式编号用等价字节算术，并逐个验证兼容性。用独立线程报告被中断线程的阶段，避免错误诊断代码也被一起截断。
