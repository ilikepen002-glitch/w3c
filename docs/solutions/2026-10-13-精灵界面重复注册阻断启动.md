# 精灵界面重复注册阻断启动

## 现象与环境

用户再次反馈怪物不出生、右上角统计缺失。截图中的独立启动检测提示为“地图启动未完成：注册精灵事件与界面”。项目使用 JASS/v1.28 配置，部署到 Warcraft III 1.27a；当前构建使用隔离的 legacy-jass-8192 编译器。

该阶段执行 `tdSetupPets()`，依次装配精灵运行时、战斗和界面。首波登记与 HUD 创建排在其后，因此此阶段中断能够同时解释两个现象。

## 之前为什么没有修好

- 之前隔离 HUD 只解除了显示与玩法启动的同步耦合，没有解决更早的精灵初始化中断。
- 之前把 rawcode 的字符串扫描改为整数运算，消除了真实的昂贵路径，但仍然逐个注册界面按钮。
- 后续收藏列表增加技能数量图标，初始化注册量从 153 增加到 515：490 个列表变体（10 格 × 每格 49 种状态）、23 个操作按钮、2 个农民入口。这些是界面按钮，不是捕获时决定精灵技能的事件。
- 旧 `VerifyPetStartupArtifact.py` 将 `registerSpellEffectEvent` 整体作为桩，只核对编号数量。因此既没有测到内部注册成本，还把 515 次注册固化为预期行为。

## 根因证据与边界

所有 513 个管理界面按钮最终调用同一个 `onCommand`。逐编号注册重复创建触发器，执行 HashMap 查询/写入、句柄转换和条件注册。当前编译产物还包含调用栈及对象有效性检查。

用同一个离线解释器执行实际打包的 UI 初始化、标准库注册和 HashMap 实现，旧图为 **96,523 条解释器语句**；修正后为 **827 条**。修正前后字符串搜索和 SubString 调用均为零，说明复发不能再归因于 rawcode 字符串扫描。

可确认的源码问题是同一处理函数被重复注册，导致启动工作量不必要地膨胀。截图的中断阶段与 JASS 线程预算耗尽高度吻合，但截图只定位到 `tdSetupPets` 阶段，不能单独证明内部精确中断指令。离线语句计数包含解释器自己的计数规则，不是引擎 operation 数；本轮未运行游戏，不宣称已实测引擎中断原因或恢复。

## 修正

- `TDPetUI.wurst` 用一个专属触发器监听施法效果，将管理界面按钮交给原有 `onCommand`；两个农民入口保留原注册方式。
- 保留显示单位身份、所属路线、已挂载技能与等级、会话快照和一次性操作校验。无关施法不得消耗会话。使用独立触发器，不依赖其他系统的条件求值结果。
- 不改变 rawcode、界面图标、物编对象、捕获技能生成、全局启动顺序或就绪协议。
- 修正离线检查的桩边界，执行真实注册/HashMap/玩家注册循环；原生引擎、句柄转换表和计时器仍明确建模。
- Windows 与 Linux 构建入口在发布前执行精灵注册及启动回归门禁。旧图的 515 次注册会失败；共享监听检查还限制此离线夹具的初始化工作量，阈值不代表引擎预算。

## 可复用经验与可提炼技能

启动回归不能只执行业务层循环而跳过循环内最昂贵的基础设施调用。检查应证明外部可观察行为和有限启动工作量，而不是要求重复注册次数恒定。大量数据变体共用同一行为时，优先共享事件入口并复用既有精确校验，而不是增加异步分片和新就绪状态。

可提炼技能：结合启动阶段检测、实际打包 JASS 的调用路径、旧图负例和显式桩边界，诊断重复性初始化开销；将验证加入发布前门禁，同时保留实机验证边界。
