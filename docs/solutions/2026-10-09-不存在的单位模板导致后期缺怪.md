# 不存在的单位模板导致后期缺怪

## 现象和环境

Warcraft III 1.27.0.52240、JASS。第12波精英诊断击杀没有产生任何金币或掉落，但地图编译和原有代码测试全部通过。进一步发现第21–24波普通怪、第20波精英、第16波护卫也引用无效模板。

生命归零后的停怪是另一种正常终局情况。不能用首波能出怪或一局已失败，推断后期所有敌人都能生成。

## 关键证据与根因

TEST-0511 的原生收益测试先通过无装备、同路+1、跨路、工人、卸装、额度截断、无击杀者和漏怪阶段，然后停在第12波精英：没有对应死亡奖励或掉落。初始测试没有先检查创建结果，把前置失败表现成了掉落失败。

读取本机 `War3Patch.mpq` 的 `Units/UnitData.slk` 与 `UnitUI.slk`，并对照已打包 `war3map.w3u`，发现以下不存在的父单位 rawcode：

| 地图单位 | 缺失父模板 | 修正 |
| --- | --- | --- |
| uE15、uE16、uE17、uE18（21–24波） | nsgu | nsgn，实际存在的海巨人 |
| uS12（12波精英） | nbst | Nbst，大小写敏感的兽王 |
| uS20（20波精英） | ordr | otau，地面牛头人 |
| uG16（16波护卫） | nsgu | nsgn |

`ordr` 无法从现有代码还原设计原意，选择 `otau` 是地面破阵精英的模型选择，而不是声称原模板只是大小写错。自定义 rawcode、波次、数量和显式生命/护甲/速度未改。

本机 `patch.mpq`、`Patch127.mpq`、`zhCN.mpq`、`War3xLocal.mpq` 均不包含 UnitData；War3Patch 的 UnitData 包含836个四字节单位ID，内容SHA256为 `34a0c8083f146b5d3e25d92a19a8822151d4b26dfe9c1c325a6229466d1b04d6`。

## 为什么既有检查没有发现

Wurst 允许构造以四字节 ID 为父项的单位定义，类型检查和地图编译未检查此父项是否存在于目标游戏版本。只检查纯波表数量、首波刷怪和掉落聚合函数，无法覆盖原生创建边界。没有使用重复重装或增加刷怪兜底等无关尝试。

## 修复与验证

- 在源码 `wurst/TDWaves.wurst` 修正父模板。
- 新增 `tools/VerifyUnitParentsArtifact.py`，从实际目标游戏MPQ提取单位目录，严格区分大小写检查全部打包单位。对旧图准确报出7项缺失，对新图82项全部通过。
- `TDNativeRewardProbe` 先逐 tick 创建32种普通怪、4种精英、4种护卫、4种Boss，检查非空、实际类型、存活、归属、波次和最大生命。移除测试单位，不触发死亡奖励。
- 对 `uS12` 额外跨一个tick观察真实位移，确认继承英雄模板后仍能移动且最大生命符合配置。
- TEST-0523（SHA256 `C1C912FF92A8D510229631DB1E5662E5EAC2ADD594FE765A528CEEFD1E72C38B`）实机输出：`REWARDS PASS enemy types=44; gold rules/cap; drop green->blue; boss unchanged phase=14`。
- `tools\Run-WurstChecks.bat` 类型检查、全部测试通过；诊断与正常产物均使用 `build-and-deploy-test-map.bat` 编译部署。
- 产物父模板检查命令：`python tools/VerifyUnitParentsArtifact.py ExampleMap.w3x "D:\War3_1.27a\Warcraft III Frozen Throne 1.27a publish\War3Patch.mpq"`。
- 按用户要求跳过 Gemini 审查，独立代理方案结论 PASS WITH NOTES；原生最大生命和移动检查已落实。

## 残余风险与可提炼技能

44种创建完整性不是32波正常经济通关，也不代表逐种模型动画和完整受击路线均已观察。新脚本验证单位父ID，不验证所有技能、模型资源或其它游戏版本。

可提炼技能：编译通过但缺单位时，先检查 CreateUnit 返回值，再从目标游戏实际 SLK 校验大小写敏感的父ID；用原生逐种创建覆盖全部对象，而不是仅验证配置表。测试掉落或战斗前，必须先验证目标真实存在。
