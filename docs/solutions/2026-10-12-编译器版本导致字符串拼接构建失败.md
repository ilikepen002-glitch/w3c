# 编译器版本与历史依赖目录导致本地构建失败

## 现象与环境

远端验收通过的源码在 Windows 执行 `build-and-deploy-test-map.bat` 时失败，首个错误是 `TDPetObjectGen.wurst:119` 的 `string + int`。常规检查随后报告同类拼接及其级联类型错误。项目目标仍为 JASS、v1.28，标准库锁定树为 `90b45617eda50c15703e8cb2ec3241d3c7b61816`。

本地旧编译器版本为 `1.9.0.0-nightly-1-g663a2e1a`，jar SHA256 为 `E582E6AF4F5808875841EC4ECE5B32178F5CF62A56489AF1873862CA1F916D62`。系统 PATH 指向 JDK17；Wurst 自带运行时为 25.0.3。

## 根因与无效尝试

1. 远端源码使用编译器新特性。[官方提交 f383a556](https://github.com/wurstscript/WurstScript/commit/f383a556fdc954b796e438f66d689ea2eb39bff6) 于 2026-08-04 加入字符串拼接的隐式 `toString`。给首个错误加显式转换只能越过一行，无法修复旧工具链与远端源码的差异；该临时改动已撤回，生产源码与任务基线一致。
2. 更新编译器后，检查通过但地图构建在 `loadLibPackage` 空指针失败。依赖扫描树内遗留 `pre1.29/WurstStdlib2_broken_backup_20260607`；递归包发现用它覆盖了全部 164 个包，而地图 ModelManager 只接受依赖根下的 `wurst/`。只读反射探针确认全部 164 个实际选中路径都被拒绝；隔离遗留目录后拒绝数变为 0。现有锁库校验只检查指定目录，不能排除额外扫描目录。历史 `pre1.29/WurstStdlib2` 的 172 个文件还被 Git 跟踪，因此干净检出也会复现错误扫描边界；仅本机移动缓存不构成持久修复。实施时没有先核实这些文件被跟踪，是一次诊断遗漏。
3. 新 jar 的编译器 class major 为 71（Java27）；显示名工具直接依赖的 W3I、JMpqEditor 为 69（Java25）。PATH JDK17 实际编译报 `bad class version 69.0, expected 61.0`。官方 jlink 运行时只有 `java.compiler`、没有 `jdk.compiler` 和 javac，不能替代完整 JDK。

## 修复与来源

- 使用 [官方 Windows nightly 包](https://github.com/wurstscript/WurstScript/releases/download/nightly/wurst-compiler-nightly-win-x64.zip)，本次资产更新时间为 2026-10-12；zip SHA256 `6BB152C7F4010F91198C861BF257C966D3FC0FE878828497444E970A841AA893`。nightly 标签元数据指向旧提交，不能代替包内实际版本核实。
- 包内实际编译器版本 `1.9.0.0-nightly-2-g82c1bd294`，jar SHA256 `365CACAF982A0B348348979031F8D70B3766E38FF315C9EAC746CE7EA68A801D`，实际 class 含 `implicitToStringForConcatOperand`。只更新 `.wurst/wurst-compiler` 与同包 `.wurst/wurst-runtime`；Grill 保持 `1.4.0.0-8845a51`。
- 安装 [官方 OpenJDK27 GA](https://download.java.net/java/GA/jdk27/55ce5470a6294008af0057ff4626d0e5/35/GPL/openjdk-27_windows-x64_bin.zip)，版本 `27+35-2325`，zip SHA256 `41172837168DD25A8D9FE5EB253AC1EFC568C5F9FF608144BCACADFDF50F876C`，与官方 `.sha256` 一致。完整 JDK 放在 `%WURST_TOOLCHAIN_HOME%/wurst-jdk`，不放进上游更新管理的 jlink runtime。
- 构建脚本在开始前检查独立 JDK 的 java/javac，显示名阶段显式调用这两个绝对路径。没有修改系统 PATH、JAVA_HOME、生产 Wurst、标准库内容或锁。
- 将非配置历史依赖 `pre1.29` 和旧顶层 `WurstStdlib2` 移出依赖扫描树，保留锁定的 `WurstStdlib2-source`。旧顶层标准库树 `5b5c8b36d8a9dbc4acc3ca48d22982a79e55bf77` 与锁不一致，不能依靠包名覆盖顺序继续共存。

## 可复用经验与可提炼技能

先比较编译器实际版本和语言特性，不把兼容问题改成大量源码补丁。版本可用 `javap -constants de.peeeq.wurstio.gui.AboutDialog` 读取；下载资产校验 hash，不能只信 rolling tag。

类型检查通过不代表地图模型依赖加载通过。遇到库解析空指针，比较实际包索引路径与允许的依赖根，检查活动扫描树里的旧目录和备份。备份应放在扫描树外，标准库锁校验与扫描树纯度是不同边界。

可提炼技能：Windows Wurst 工具链兼容检查（实际版本、class major、Grill 子进程、jlink 与完整 JDK区别）、库路径覆盖诊断，以及保留内容的依赖隔离与构建产物 hash 验证。
