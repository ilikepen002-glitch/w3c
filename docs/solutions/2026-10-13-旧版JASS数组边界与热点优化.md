# 旧版 JASS 数组边界与运行时热点优化

## 问题与环境

装备整合版 `ce64984` 的 Wurst 测试通过，但实际地图中 129 个类分配函数使用 `maxIndex < 32768`，随后先自增再写数组。上一版也有 100 个相同分配器，因此不是装备整合新引入的问题。

项目目标是 JASS / `wc3Patch: v1.28`，本机实际部署客户端为 Warcraft III 1.27a。游戏 MPQ 和项目 common.j 均定义 8192 个数组槽位，有效下标为 0..8191；Wurst 对象保留编号 0。原保护会允许越界分配，但不能由此推断开局必然崩溃，实际触发还取决于每个对象池的同时占用情况。

基线编译器为 `1.9.0.0-nightly-2-g82c1bd294`，完整源码基线为 `82c1bd2940e5559df1cf8769cd8652e899066836`；使用 Java 27。安装的 Grill 为 `1.4.0.0-8845a51`，不能拿本地不同版本的 Grill 源码当作其行为证明。

## 关键线索与无效方向

- 直接从当前、上一版地图 MPQ 提取脚本，确认问题已有且实际产物受影响；只看 Wurst 业务源码和解释器测试不够。
- 原编译器已有读取 `JASS_MAX_ARRAY_SIZE` 的代码。继续往前追编译阶段，发现生成类分配器前的 TreeShaker 已将此时无人引用的容量常量删除，分配器因此选择 32768 默认值。
- 项目本来就选择了旧版 common.j，单改补丁配置无法解决这个阶段顺序问题。
- `-legacyJassChecks` 只放宽特定旧 JASS 类型检查，不负责数组容量。
- 机械地把比较常量改为 8192 仍会越界：比较发生在自增前，应限制到容量减一。
- 普通构造器和闭包分别生成分配与初始化代码；只修普通构造器会漏掉闭包捕获字段及 super 初始化。
- 默认错误处理可以报告后返回，因此必须处理分配返回 0 的路径，不能假定错误必然终止线程。
- 验证器只查找安全代码片段并不可靠：函数的其它位置仍可能插入危险写入。最终改为识别完整函数形态，并用恶意插入变体验证拒绝行为。

## 最终修改

编译器缺陷在独立源码仓库 `E:/WurstToolchain/WurstScript-source` 修复，补丁和重建说明保存在 [tools/compiler](../../tools/compiler/README.md)：

1. TreeShaker 保留后续分配器需要的目标容量常量。
2. 专用旧版 JASS 编译器的默认容量及成员数组展开容量为 8192；分配器使用容量减一的边界，空闲槽位优先复用。
3. 分配失败时保留池状态；普通构造器、闭包均禁止继续初始化零号对象。
4. 使用独立安装目录 `E:/WurstToolchain/legacy-jass-8192`，不覆盖全局编译器。锁定编译器、Grill 和源码补丁哈希，并查询安装 Grill 的公开 API，确认实际启动路径。
5. 正式构建在显示名修改之后、发布根地图及部署之前，只读检查 MPQ 中的脚本。所有分配器均需匹配已知安全完整形态；允许类型数组被树摇同时移除的形态，拒绝单边缺失、额外写入、错误容量和无法识别的形态。检查前后核对地图哈希。

运行时优化保持现有职责和生命周期：

- 光环：把目标路线、位置、机械属性和冷却资格读取移到每目标刷新内，避免在每个源/装备槽重复查询；保留 try、聚合后提交和 buff 重试。
- 装备：通过 Table 按目标句柄索引已有减益记录，攻击查询从 O(N) 变为 O(1)；同次攻击复用 entry 和时钟。记录析构统一清索引，链表继续决定 tick 顺序。
- 分裂箭：先判断候选能否入选，再创建 shot 和捕获试炼上下文；被拒绝候选不再分配对象。同距顺序、替换规则与析构归属不变。

具体复杂度、固定成本及未改热点见 [性能记录](../validation/2026-10-12-runtime-hotpaths.md)。未把源码工作量减少解释为实测 FPS 提升。

## 可复用经验与可提炼技能

- 兼容问题从“实际 MPQ 脚本 → 游戏 common.j → 编译阶段”逆向定位，不能用单元测试成功替代后端兼容证明。
- 追查配置为何失效时，检查其值是否在真正消费前被消除；看到已有读取代码不代表通路有效。

- 可提炼技能：旧版 JASS 后端容量审计、隔离编译器锁定、实际脚本回放与最终部署脚本哈希等价验证。
